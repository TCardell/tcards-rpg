# Preparar Codex y Supabase de desarrollo

Guía operativa para el propietario. No implica que Codex esté conectado o que se haya iniciado un trabajo. Estado inicial: proyecto Supabase TCards RPG creado, repo GitHub TCardell/tcards-rpg público, aún sin integración verificada; comprobar estado antes de cualquier cambio.

## Preparación
1. Abrir Codex de escritorio/local con la cuenta del propietario y el repositorio clonado, rama main actualizada. Alternativa entorno Cloud si permite conexión segura y pruebas suficientes. Permitir trabajo en el repo y dependencias necesarias; no otorgar acceso global al ordenador ni desactivar sandbox/confirmaciones. Usar cuota Plus disponible sin comprar créditos.
2. Consultar documentación oficial de Supabase [MCP](https://supabase.com/docs/guides/ai-tools/mcp) y [AI Tools](https://supabase.com/docs/guides/ai-tools); seleccionar cliente Codex y seguir configuración actual. Proyecto permitido: TCards RPG, ref ocnvfivxbnbypjfhpnlx. La conexión de ChatGPT no garantiza acceso desde Codex.
3. Primero conectar con URL de proyecto en lectura: https://mcp.supabase.com/mcp?project_ref=ocnvfivxbnbypjfhpnlx&read_only=true. Autorizar OAuth en navegador y comprobar que lista únicamente recursos esperados. No incluir tokens ni contraseñas en prompts/repo. Usar conexión restringida al proyecto, no toda la organización. Para aplicar cambios aditivos de desarrollo, propietario autoriza explícitamente conexión de escritura al mismo proyecto (URL sin read_only), revisa las solicitudes sensibles y mantiene confirmaciones. Alternativa: Supabase CLI autenticada localmente, vincular solo al proyecto dev tras verificar referencia. Seguir docs vigentes y --help, probar migraciones local primero cuando viable. No usar otros proyectos ni prod.
4. Configurar URL pública del proyecto y publishable key en .env local ignorado por Git, conforme .env.example; no usar service role en frontend. Secretos de servidor únicamente en entorno seguro/dashboard, no chat, logs, PR o Git. Crear usuarios de prueba ficticios con proceso autorizado; no desactivar RLS, no debilitar Auth ni exponer datos reales.

## Lanzamiento
Leer docs/FIRST_TASK.md (encargo maestro y criterios de terminado). Si el cliente ofrece Goals, pedir a Codex que use ese documento como objetivo duradero y revisar que los límites y condición de terminado coincidan; activar goal según la UI/versión actual. Ver [Using Goals in Codex](https://developers.openai.com/cookbook/examples/codex/using_goals_in_codex). Si no está disponible, usar tarea larga normal. No hay promesa de duración ni cuota. Mantener checkpoints en PROGRESS.md y Git, retomar desde ese estado tras interrupción.

Para solo cuando el objetivo esté verificado, se agote la cuota o haya un bloqueo real; no declares completo lo no probado. Si Goals está disponible, adopta este objetivo duradero.

## Reanudación
Lee PROGRESS.md, git status, historial y resultados de pruebas. Comprueba qué cambios están en rama y qué migraciones se aplicaron realmente. Continúa por el siguiente criterio de aceptación incompleto, sin repetir pasos ni duplicar seed/migraciones. No asumir que una nueva sesión conserva credenciales o contexto. Si un acceso falla, no pedir secretos por chat; guiar autorización oficial. Mantener el coste en 0 adicional salvo aprobación.
